## 3. Current architecture

`[IMPLEMENTED]` A two-tier modular monolith:

- **Next.js client.** Every page is a client component (`"use client"`). All API calls go through `frontend/lib/api-client.ts`. JWTs are stored in `localStorage` (`frontend/lib/auth.ts`).
- **Django REST API** mounted at **both** `/api/v1/` and `/api/` (`backend/config/urls.py:13-14`).
- **One shared database.** Tenant isolation is done in application code via `Library.owner` (OneToOne) and `IsLibraryOwnerOf`.

`[INFERENCE]` There is no service layer. Business logic lives in serializers (`apps/libraries/serializers.py:137-228`) and views (`apps/seats/views.py:41-104`).

## 16. Broken or incomplete behaviour

1. **`backend/requirements.txt` cannot reproduce the environment** (§2). Tests pass only because the auditor's machine has DRF, SimpleJWT, cors-headers and decouple installed globally.
2. **`backend/.env.example` is empty** (0 bytes), although `AGENTS.md` §11.1 specifies its contents.
3. **`frontend/.env.example`** sets `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000/api` (not `/api/v1`). It only works because of the duplicate `/api/` mount.
4. **Booking button is fake:** `app/student/library/[id]/page.tsx:577-579` calls `alert()`. This violates `AGENTS.md` §1 directive 3.
5. **Hardcoded facilities** in `app/student/library/[id]/page.tsx:266-272` and `app/student/discover/page.tsx:609-614`. Every library shows the same amenities, which is fake data.
6. **Cosmetic shift selector** with hardcoded hours (`components/seat-map/SeatGrid.tsx:16-21`). Changing shift changes nothing.
7. **Domain breakdown always returns zeros.** `apps/libraries/serializers.py:60-70` and `views.py:205-215` import a `Membership` model that does not exist, and a bare `except Exception` hides the `ImportError`.
8. **Session silently expires** `[INFERENCE]`: SimpleJWT's default access lifetime is 5 minutes, and the frontend never refreshes the token. Owners get 401 errors mid-wizard.
9. **Owner setup wizard data integrity** (`app/owner/setup/page.tsx:303-313`, `apps/libraries/serializers.py:184-226`):
   - Removing a seat in the UI does not delete it on the server (the backend only upserts).
   - Each save re-upserts **every** seat with the status held in the UI. This can overwrite live `reserved`/`occupied` statuses.
   - Re-applying `seat_layout` resets matching seats to `empty`.
   - Each save **deletes and recreates all pricing plans** (`serializers.py:194-202`), which changes plan IDs. Once memberships reference plans through a FK, this will either fail (PROTECT) or destroy history.
10. **Unvalidated seat statuses:** `apps/seats/views.py:48-73` and `apps/libraries/serializers.py:158-165` accept any `status` string from the client without checking choices.
11. **Possible unhandled 500s** `[INFERENCE]`: nested `pricing_plans` items are unvalidated `DictField`s converted with `int()` and decimals (`serializers.py:148-153`). Non-numeric input raises inside the transaction.
12. **Seeded data is inconsistent:** seats are seeded as reserved or occupied with no membership behind them.

## 18. Architecture problems

1. **A single static `Seat.status` cannot express time.** Reservations need an expiry, and shift-based booking (if adopted) needs per-shift availability. Today `reserved` persists forever, and SRS §3.3 hold-timeout cannot work without a reservation record.
2. **No service layer.** Domain rules live in serializers and views, so booking, payment and archival logic will be hard to test and to reuse.
3. **No global DRF configuration:** no exception handler (envelope is inconsistent), no default permission (AllowAny), no pagination, no throttling.
4. **N+1 discovery query.** `GET /libraries/` serializes every library with 4 seat-count queries each, then filters by radius in Python. `[INFERENCE]` This will degrade as libraries grow (SRS NFR-04).
5. **SQLite is the only exercised DB.** `select_for_update` is a no-op on SQLite, so concurrency guarantees cannot be verified there. Concurrency tests must run on PostgreSQL.
6. **Frontend structure:** monolithic pages (the setup page is 1341 lines), all inline styles, no shared UI kit, no auth context or route guards, `strict: false`, and `any` used (against `AGENTS.md` §2.3).

- `User.phone` is not unique or normalised. `is_offline_student` and `updated_at` are missing.
- `Library.latitude/longitude` default to `0.0` ("null island") instead of NULL, so unlocated libraries pass proximity math.
- `Library.total_seats` is denormalised and can drift (the seed and three sync paths write it).
- `domains_catered` is a comma string and `User.domain` is free text. There is no shared vocabulary, so analytics match by exact string.
- `PricingPlan` has no `is_active`. The destructive replace (§16 item 9) is incompatible with FK history.
- `Seat` has no position fields (SRS §2.5 asks the model to "support a future editable floor plan") and no soft-disable, so deleting a seat would orphan or cascade history.
- No constraint for "one active membership per seat (per period)". This must be designed (partial unique index or exclusion constraint) in Phase 3.
- **SPEC-level issues** (not yet code): `Membership.library` and `Payment.library` use `on_delete=CASCADE` (`SPEC.md` §4.2), which would erase financial history and contradict SRS NFR-07. Notification and NotificationLog are merged into one entity yet referenced separately, and the unique key differs between `SPEC.md` (includes `recipient`), `FEATURES.md` (`membership, milestone, date`) and `AGENTS.md` §6.

## 21. API problems

- The envelope is inconsistent: auth endpoints and DRF validation errors return raw DRF shapes, and one error adds an extra `existing_library_id` key (`apps/libraries/views.py:106`).
- Duplicate mounts and routes (§17). PUT behaves as PATCH.
- No pagination on `GET /libraries/`.
- Endpoint naming differs across documents (§25 C9 to C12).
- Duplicate library creation returns 400 rather than 409.

## 22. Frontend problems

- No login, register, dashboard or owner-management pages. Owner login lives inside the setup wizard with demo credentials.
- No auth context, role-based navigation or route protection. No token refresh.
- Fake data: hardcoded amenities, hardcoded shift hours, `alert()` booking.
- Inline styles everywhere, no design system or Tailwind (SPEC promises Tailwind), very large page files.
- `tsconfig.json` has `"strict": false`, and `any` is used in catch blocks and `ApiError.data`.
- No `loading.tsx` or `error.tsx` route files. No frontend tests. No ESLint.
- Discovery has no map view (SRS FR-03: "map/list").
